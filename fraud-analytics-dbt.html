Fraud analytics · SQL · dbt · DuckDB

Building a fraud analytics warehouse.

I built this project to take transaction-level fraud data beyond a collection of raw files. I used dbt and DuckDB to create a repeatable SQL pipeline, investigate identity and device coverage, and produce a tested reporting layer that makes the underlying patterns easier to work with.

The project

From raw transactions to something I can analyse.

I wanted to build a small but realistic analytics engineering workflow, rather than just write a few queries against a CSV. The project takes transaction data and supporting identity and device information through a set of dbt models, with a final mart designed for fraud analysis.

I used SQL for the transformations, DuckDB as the local warehouse and dbt to organise the models, manage dependencies and run data quality checks. I also added incremental processing and snapshots so I could work through how a pipeline handles new records and changes to existing ones.

The main focus is the analytical foundation: understanding what information is available, making the transformations repeatable and checking that the outputs are reliable. This is a fraud analytics warehouse, not a trained machine-learning classifier.

How I structured it

A layered dbt project.

I split the transformations into stages so each model has a clear job. That makes the SQL easier to maintain and gives me a straightforward way to trace a reporting figure back through the pipeline.

01 · SOURCES

Raw data

I brought the transaction, identity and device data into DuckDB as source tables. This gives the project a consistent starting point for the transformations.

02 · STAGING

Clean and standardise

I used staging models to select and standardise the fields needed downstream, including transaction identifiers and identity attributes.

03 · INTERMEDIATE

Join and shape the data

I separated the more involved joins and analysis logic into intermediate models, including transaction identity, identity fraud analysis and device fraud analysis.

04 · MART

Reporting layer

I brought the outputs together in a fraud performance mart, with transaction volumes, fraudulent transaction counts, fraud rates and average transaction amounts.

Why I used layers: I can change or test one part of the pipeline without burying all the logic in a single query. The dbt dependency graph also makes it easier to see how the reporting model is built.

02 · INTERMEDIATE JOINmodels/intermediate/int_transaction_identity.sql

This is the core join in the reporting path. I kept every transaction with a LEFT JOIN, then used CASE expressions to distinguish missing identity records from missing device data.

SELECT

    -- Transaction identifiers and attributes
    t.TransactionID,
    t.TransactionDT,
    t.TransactionAmt,
    t.ProductCD,

    -- Fraud outcome
    t.isFraud,

    -- Identity and device attributes
    i.DeviceType,
    i.DeviceInfo,

    -- Identity availability
    CASE
        WHEN i.TransactionID IS NOT NULL
            THEN 'Available'
        ELSE 'Unavailable'
    END AS identity_status,

    -- More detailed device data availability
    CASE
        WHEN i.TransactionID IS NULL
            THEN 'No identity record'

        WHEN i.DeviceType IS NULL
            THEN 'Identity exists, device missing'

        ELSE 'Device information available'
    END AS device_data_status

FROM {{ ref('stg_transactions') }} AS t

LEFT JOIN {{ ref('stg_identity') }} AS i
    ON t.TransactionID = i.TransactionID
03 · INCREMENTAL MODELmodels/intermediate/int_transactions_incremental.sql

I configured this model to merge on TransactionID. The incremental filter uses the current maximum ID as a simple watermark for the exercise.

{{
    config(
        materialized='incremental',
        unique_key='TransactionID',
        incremental_strategy='merge'
    )
}}

SELECT
    TransactionID,
    TransactionDT,
    TransactionAmt,
    ProductCD,
    isFraud

FROM {{ ref('stg_transactions') }}

{% if is_incremental() %}

WHERE TransactionID IN (
    SELECT TransactionID
    FROM {{ ref('stg_transactions') }}
    WHERE TransactionID >= (
        SELECT COALESCE(MAX(TransactionID), 0)
        FROM {{ this }}
    )
)

{% endif %}
04 · REPORTING MARTmodels/marts/mart_fraud_performance.sql

The mart groups the joined data by identity and device availability, then calculates volumes, fraud rates and transaction values for reporting.

{{
    config(
        materialized='table'
    )
}}

SELECT

    -- Dimensions
    identity_status,
    device_data_status,

    COALESCE(DeviceType, 'Unknown') AS device_type,

    -- Transaction volume
    COUNT(*) AS total_transactions,

    -- Fraud volume
    SUM(isFraud) AS fraudulent_transactions,

    -- Fraud rate
    {{ calculate_percentage(
    'SUM(isFraud)',
    'COUNT(*)',
    2
) }} AS fraud_rate_pct,

    -- Transaction value
    ROUND(
        AVG(TransactionAmt),
        2
    ) AS average_transaction_amount,

    ROUND(
        SUM(TransactionAmt),
        2
    ) AS total_transaction_amount,

    -- Value associated with transactions labelled as fraud
    ROUND(
        SUM(
            CASE
                WHEN isFraud = 1
                THEN TransactionAmt
                ELSE 0
            END
        ),
        2
    ) AS fraudulent_transaction_amount

FROM {{ ref('int_transaction_identity') }}

GROUP BY
    identity_status,
    device_data_status,
    DeviceType

Making the pipeline reliable

Incremental processing, snapshots and tests.

INCREMENTAL MODELS

Process changes, not just the full table

I built incremental models and tested them with a small simulated transaction feed. I inserted a new transaction and changed an existing transaction amount, then checked that the model reflected the update without losing the unchanged records.

SNAPSHOTS

Keep a record of changes

I added a dbt snapshot for the simulated transactions and changed an amount between runs. The snapshot retained the earlier version and recorded the newer version with validity timestamps.

REUSABLE MACROS

Reduce repeated SQL

I introduced a Jinja macro to generate identity attribute columns, rather than manually repeating the same transformation for each identity field.

DATA QUALITY TESTS

Check the outputs automatically

I added checks for non-null and unique transaction identifiers, accepted fraud flag values, valid fraud rates, positive transaction amounts and consistency between fraud counts and the underlying data.

What I took from it

The data model is only as useful as the data behind it.

The biggest thing I found was how much information was missing from the identity and device fields. That has a direct impact on the kind of analysis I can do and how confidently I can interpret the results.

Building the warehouse also gave me practical experience with dbt features that are useful in a production-style workflow: model dependencies, incremental merges, snapshots, macros and automated tests. I could test the behaviour with simulated changes and inspect the results directly in DuckDB.

If I took this further, I'd focus on more detailed data profiling, monitoring coverage over time, and adding tests around the assumptions used in the fraud reporting layer. I'd also investigate why identity and device information is absent for such a large share of transactions before treating those fields as representative.
